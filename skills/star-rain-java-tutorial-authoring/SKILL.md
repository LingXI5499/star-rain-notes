# 星雨笔录 JavaSE 教程生产

目标是生成接近 `C-Resource` 阅读节奏、并适配星雨笔录网站的 JavaSE 教程：目录清楚、解释直接、示例够用、提醒来自真实问题，读者能够按顺序学习并通过问题与练习检查掌握情况。

## 先判定任务

- `AUDIT`：只报告目录、边界、编号、重复和冗余问题，不改正文。
- `OUTLINE`：只给章节边界和知识点清单，不扩写正文。
- `AUTHOR`：生成或重构公开章节，并输出内部生产记录。
- `REVIEW`：按结构、技术、教学和边界门禁检查现有章节。

用户未指定模式时，根据请求选择最小必要模式。分析或审核请求不自动改写文件。

## 两类来源不能混用

### 决定“值不值得教”

按以下顺序判断：

1. Java 基础学习的先后依赖；
2. 当前秋招、实习和初级 Java 岗位的高频考点；
3. 真实项目和日常开发的使用频率；
4. 用户旧教程、题库和代码资产的覆盖情况。

只满足“新版本有这个语法”不构成进入核心主线的理由。`var`、JShell 等便利性内容默认不进入核心章，除非用户明确要求或真实项目确有依赖。

### 决定“讲得是否正确”

技术事实以 JDK 21 的 JLS、JVMS、Java SE API、JDK Docs、Dev.java 与 OpenJDK 为准。面经、教程站和旧资料只能证明需求或帮助查漏，不能覆盖官方语义。

详细规则见 [references/knowledge-selection-policy.md](references/knowledge-selection-policy.md)，课程上下文见 [references/java-course-context-v4.md](references/java-course-context-v4.md)。

## AUTHOR 工作流

1. 从 Course Manifest 锁定课程分组、章节、上一章、下一章和禁止展开的内容。
2. 为候选知识点记录学习依赖、秋招信号和工作信号，删除低频便利功能、版本猎奇和重复项。
3. 保持四个固定正文板块，再根据章节类型选择板块内部写法：
   - 语法 / API：短解释 → 必要的表格或语法 → 带注释示例 → 少量真实提醒；
   - 安装 / 工具：目标与前提 → 编号步骤 → 验证结果 → 必要排错；
   - 原理 / 说明：先给结论 → 关系或流程 → 必要边界；代码可以没有；
   - 对比 / 选型：先给选择结论 → 对比表 → 典型场景 → 易错边界；
   - 综合练习：场景 → 要求 → 起始代码（按需）→ 验收标准。
4. 按 [references/chapter-authoring-standard.md](references/chapter-authoring-standard.md) 控制标题与编号，按 [references/writing-patterns.md](references/writing-patterns.md) 选择适合的正文形态。
5. 对公开可运行代码使用 JDK 21 实际编译或运行。故意错误的代码必须标注“错误示例”。
6. 运行 `python scripts/validate_chapter_structure.py <chapter.md>`，修复错误并审查警告。
7. 按 [references/review-gates.md](references/review-gates.md) 自审。AI 最多标记 `READY_FOR_HUMAN_REVIEW`，不得伪造人工批准。

## 公开章节硬规则

- 元数据只有 `title` 和 `summary`。网站先把它们渲染为页面 H1 和标题下摘要，正文不得重复 H1 或摘要。
- 每篇公开文章的正文必须且只能依次出现四个 H2：`## 一、学习目标`、`## 二、核心知识`、`## 三、问题`、`## 四、练习题`。
- `二、核心知识` 下只有真正的知识点使用 H3：`### 2.1 ...`、`### 2.2 ...`；每篇章节都从 `2.1` 重新编号。
- 其他板块需要细分时同样跟随父级编号，例如 `### 4.1 代码阅读`；不需要细分时直接使用列表或段落。
- 只有真实的子知识点才使用 H4 `2.1.1`；默认优先用段落、列表、表格和代码注释，避免继续拆标题。
- 禁止把“定义、作用、语法、代码示例、注意事项、一句话解释、常见错误、最终认知模型”机械地做成标题。
- 对语法或 API，开头用一小段同时说清“是什么、怎么写、用在哪里”；可用一句话说清时不得拆成多段。
- 代码紧跟解释，完整、最小、可运行，并添加帮助理解当前知识的注释；不逐行翻译显而易见的代码。
- 注意事项不是必填栏目。只有真实开发故障、编译/运行错误、数据风险或高频秋招混淆才写，通常 0～3 条。
- 安装、IDE、流程、原理和说明性内容仍使用同样四个 H2，但“核心知识”内部不强制提供代码，也不套语法知识点的写法。
- 多项规则或选择适合用表格；明确流程适合用有序步骤；关系和原理按认知顺序解释。
- 不另建重复总结栏目，不提前讲下一章负责的内容。
- 默认正文 2,000～6,000 字符；超过 8,000 必须压缩或说明，超过 12,000 视为结构失败。
- 问题默认 5～10 个；练习按章节特点选择代码阅读、代码编写、操作验证或原理判断，不强制每类都出现。

`C-Resource` 只作为目录节奏、短解释、最小示例和少量提醒的风格参考，不作为 Java 技术事实来源。

## 输出要求

`AUTHOR` 默认交付：

1. 公开章节；
2. 内部生产记录，至少包含边界、知识点清单、章节类型、来源、代码验证、已知待办与状态；
3. 校验结果摘要。

不要把 Source Map、答案键、审核日志或运行日志写进公开正文。
