# 星雨笔录通用教程写作

将一个主题组织成能够循序学习、实际操作并检查掌握情况的教程。教学方法通用于不同学科；具体版本、事实来源、示例形式和验证工具由本次主题决定，不预设编程语言、就业目标或运行环境。

## 确定任务与课程边界

- `AUDIT`：报告目录、边界、编号、重复和遗漏问题；不自动改正文。
- `OUTLINE`：规划章节边界、知识点与前后依赖，不扩写完整正文。
- `AUTHOR`：生成或按请求重构章节，交付内部生产记录。
- `REVIEW`：检查现有章节的结构、事实、教学价值与验证证据；审核请求不自动改写文件。

从用户材料和 Course Manifest 确定主题、读者基础、学习目的、版本或环境、上一章、下一章及禁止提前展开的内容。没有目录时先给出合理的本章边界；只有影响正确性或教学范围的缺失信息才需要澄清。考试、求职、工作实践或兴趣学习按用户目标选择，不把某一种目标设为所有教程的前提。

## 选材与来源

“值得教”取决于学习依赖、目标任务中的使用频率、关键误解或错误成本、用户已有内容的覆盖情况。“讲得正确”取决于适用版本的规范、官方文档、学科权威资料及可复现证据。新版本增加了功能，不足以证明该功能应该进入主线。

选材或审计时读 [知识点准入与来源规则](references/knowledge-selection-policy.md)。教程正文的结构与编号读 [章节标准](references/chapter-authoring-standard.md)，按主题选择 [写法](references/writing-patterns.md)。

**只有涉及 JavaSE 课程时**才按需读 [Java 课程上下文](references/java-course-context-v4.md)。其中 JDK 21、秋招重点和既有章节修订属于该课程的条件性约定，不能套用于其他教程；另一个 Java 课程也应以其实际目标与版本为准。

## 编写与验证

1. 锁定本章边界，给每个核心知识点记录学习价值与事实依据，删去重复、越界和无实际收益的内容。
2. 默认采用星雨笔录四块正文。用户明确要求其他教程结构时按要求组织，不把默认模板作为所有教材的硬性限制。
3. 按章节类型组织核心知识：语法/API 使用解释与最小示例；安装/工具使用前提、步骤、预期结果与必要排错；原理使用关系与因果；对比使用选择依据；实操使用材料、过程与验收条件。非编程主题可以完全没有代码。
4. 验证实际交付的示例：代码使用对应语言和依赖版本运行；命令或操作步骤核对环境、输入与结果；计算核对推导与单位；无法实测时记录未验证项。故意错误的例子明确标注用途，不能把文档查证等同于实测。
5. 使用默认四块结构时运行 `python scripts/validate_chapter_structure.py <chapter.md>`，修复结构错误并逐项判断警告；用户自定义结构不使用这个固定结构检查器判错。脚本只检查格式，不能证明事实或示例正确。
6. 按 [审核门禁](references/review-gates.md) 自审。AI 可标记 `REVISE` 或 `READY_FOR_HUMAN_REVIEW`，不得伪造人工批准。

## 共同写作约定

- 星雨笔录章节元数据默认只有 `title`、`summary`，页面已渲染标题与摘要，正文不重复 H1。其他输出环境按其实际约定处理。
- 默认四个 H2 依次为 `一、学习目标`、`二、核心知识`、`三、问题`、`四、练习题`。H3 使用父级编号，例如 `2.1`，每篇重新计数；H4 只用于真实子知识点。
- 标题用于导航，不机械重复“定义、作用、语法、示例、注意事项”等写作标签。知识点直接解释概念、用途与关键边界，步骤明确时写步骤，多项规则适合表格。
- 示例围绕当前知识，代码注释解释意图与易错行为；操作、原理和非编程知识不强加代码。提醒通常 0～3 条，必须对应实际错误、关键边界或读者容易混淆的问题。
- 问题检查理解与判断；练习训练应用，给出输入或材料、任务与可核对的验收条件。不得要求尚未讲授的前置知识，也不为凑类别强加编程练习。
- 默认正文 2,000～6,000 字符，超过 8,000 复核是否拆章；默认结构检查器将超过 12,000 视为结构失败。篇幅与问题数量是星雨笔录默认模板约定，用户指定其他规模时说明采用的结构与检查方式。

## 交付

`AUTHOR` 默认交付公开章节、内部生产记录和检查摘要。内部记录包含读者与目标、章节边界、知识点、章节类型、来源、实际验证方式与结果、待办和状态；没有运行代码的主题不填写虚假的“代码验证通过”。Source Map、答案键、审核日志和运行日志留在内部资料，除非用户另有明确要求。
