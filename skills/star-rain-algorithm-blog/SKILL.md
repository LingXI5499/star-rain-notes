# 星雨笔录算法博客

目标是让读者理解算法为什么成立，并能只看中文执行步骤独立复现实现。题目来源不限于 LeetCode，不把平台题号、难度、`Solution` 类或函数提交方式当作所有题目的前提。

## 按请求确定范围

- **写作 / 重构**：交付真实的 Markdown 正文文件、独立的标题摘要标签和验证记录。
- **审查**：检查题意、推导、代码、测试和格式，给出问题及位置；用户未要求修改时不重写文件。
- **发布信息**：仅整理标题、摘要、英文逗号分隔的标签，不生成或修改正文。

先使用用户提供的题面、草稿、代码和图片。对平台来源、题号、难度、约束或原题链接不确定时核对原始来源，不编造官方信息。自拟题和实际问题应明确输入输出契约、假设与建模边界，不能套用不存在的平台签名。

用户要求优先。若项目还有课程管理约定，技能只负责博客质量，不据此宣布学习完成。文章生成也不自动授权发布、部署或 Git 推送；已有明确授权的动作按请求执行。

## 按需读取资源

- 正文写作或重构前读 [写作与推理标准](references/writing-standard.md)：题意、黑盒与白盒测试、逐解法展开及选型。
- 输出星雨笔录 Markdown 时读 [渲染规范](references/star-rain-markdown.md)：代码页签、公式、图片及标题分工。
- 验证代码或审查质量时读 [验证标准](references/verification-standard.md)：静态检查、实际运行和正确性依据的区别。
- 需要成稿骨架时使用 [文章模板](assets/ARTICLE_TEMPLATE.md)，仅整理发布字段时使用 [发布信息模板](assets/METADATA_TEMPLATE.md)。模板提示必须替换，不照抄占位内容。

## 写作与重构流程

1. **锁定契约。** 说明问题、输入、输出、合法范围、示例及来源。区分函数 / 类提交、标准输入输出和自定义接口：函数型保留实际签名，竞赛型给完整输入输出程序，工程型明确返回约定和失败处理。
2. **先建立测试。** 给出输入、核实过的期望输出和测试目的；黑盒覆盖等价类与边界，白盒对应随后实现的真实分支。题目不允许的输入作为工程扩展另写，不混入原题约束。
3. **逐解法推导。** 默认顺序为题目描述 → 测试用例 → 若干解法 → 总结。每个解法按核心思想 → 执行步骤 → 必要的推演 / 正确性依据 → 代码实现 → 复杂度分析展开。正文从 H2 开始，标题由网站字段提供；用户明确指定其他结构时遵从，并说明标准结构检查不适用的部分。
4. **解释优化依据。** 从自然的基础方法说明瓶颈，再展示有实质价值的替代方案，不凑解法数量。分别讨论复杂度、常数、可读性与扩展性；一种方法可以成立，其他方案也不必全面更快。
5. **对齐步骤与代码。** 步骤写清变量含义、初始化、循环范围、分支、状态更新、终止和返回。剪枝、贪心、二分、DP 等关键决策要有可检验依据，短样例不能替代普遍正确性证明。
6. **完成实现与分析。** 默认每解法提供 C / C++ / Java / Python / JavaScript 五语言代码组，算法与边界语义一致；用户明确选择语言时只输出该组合。关键注释解释原因，复杂度紧随本解法，包含递归栈、复制和实际分配开销。JavaScript 数值精度、C/C++ 溢出与内存、Python 递归等按真实约束处理。
7. **核验并交付。** 标准结构用 `python scripts/validate_article.py <article.md>` 检查；指定语言时增加 `--languages cpp,python` 等参数。结构通过不代表代码正确：在可用环境实际编译 / 运行，核对测试期望，有可信参考时做可复现对拍，明确未运行项。交付正文文件、发布信息和实际验证摘要。

## 发布与质量边界

- 标题以真实题名和核心方法为主；平台 / 题号仅在确有来源时加入。摘要描述文章实际内容，标签按题型和来源选取，不给所有文章添加 `LeetCode`。
- 保留用户已有的真实媒体地址，不伪造已上传图片、平台通过记录、覆盖率或性能排名。
- 总结比较各解法的时间、额外空间、优点、限制和适用场景；推荐由约束及证明支持。
- 静态格式错误、算法错误、预期值错误和跨语言语义冲突分别修正，不把编译通过或结果偶然一致当作完整正确性证明。
