# 算法题解验证和交付门禁

## 1. 验证分三层，不要互相冒充

| 层级 | 检查内容 | 怎样得到结论 |
|---|---|---|
| 静态结构 | 标题、方法顺序、代码组格式、语言围栏、注释覆盖提醒 | `scripts/validate_article.py` |
| 编译/运行 | 代码语法、平台签名兼容、同一算法结果、不同输入输出 | 本地 GCC/G++/JDK/Python/Node 实际执行 |
| 算法正确性 | 选用数据结构是否恰当、复杂度上界、证明、暴力对拍、测试期望值 | 人工/工具结合验证，不能仅凭编译通过 |

没有环境便报告“**未验证**”，不要给出“通过 15000 次测试”式未经运行的数字。针对任何性能提升，若没有稳定基准对照只陈述复杂度或可能的常数开销变化。

## 2. Python 静态脚本

在 Skill 根目录执行：

```bash
python scripts/validate_article.py /path/to/article.md
```

或要求把缺少充分注释视为错误：

```bash
python scripts/validate_article.py /path/to/article.md --strict-comments
python scripts/validate_article.py /path/to/article.md --languages cpp,python
```

脚本检查：
- 顶级正文段落以 `## 一、题目描述` 开始，第二节是测试，最后是总结。
- 每一个解法内部顺序：核心思想、执行步骤、代码实现、复杂度分析。
- 每个解法恰有一个代码组，标签与语言围栏顺序一致；默认五语言，`--languages` 可指定组合。
- 代码块不为空、`::: / ``` ` 格式正确、不出现明显 HTML 空格实体和字面换行。
- 对中文注释不足作警告（启用 strict 时作错误）。

**限制：静态检查不能证明代码能运行，也无法判断预期结果是否真实。**

## 3. 编译/运行标准

依据题目的真实输入输出契约验证：函数 / 类提交使用隔离的**测试包装程序**，不把测试入口混入提交代码；标准输入输出题执行完整程序并比较 stdout；自拟接口核对参数、返回和失败约定。可用编译环境示例：

- C：`gcc -std=c11 -Wall -Wextra -O2`；在支持时额外用 `-fsanitize=address,undefined` 查未定义行为/内存问题。
- C++：`g++ -std=c++17 -Wall -Wextra -O2`（或与目标平台兼容的较新稳定标准）。
- Java：`javac` 与 `java`，仅在测试包装文件名需要时把 `class Solution` 放入临时 `Solution.java`；不强迫 public 类改名。
- Python：`python3`，测试脚本导入或执行 Solution；如使用 `List` 类型标注，注意 `from typing import List`，或者清楚说明平台已提供。
- JavaScript：`node`，通过包装/`eval` 执行代码后调用函数；检查对象数值精度、类型和比较语义。

若所选语言的运行环境不齐备：运行可用项，报告缺失项；绝不把跳过当作通过。

## 4. 测试设计层次

- **确定性黑盒**：至少每种有意义的输入类别 1 组；用例表里所有预期值要先独立核算。最小长度、重复、0、最大允许规模、边界附近数据、典型反例按题目约束选取。
- **白盒路径**：代码写好后对照每种解法的实际 `if/else` 和循环出口，列出触发条件的样例；无需假称获得分支覆盖率。
- **随机对拍**：有可信暴力算法时，先用它核验小规模随机样例，后让所有优化解法与参考结果比较；设置可重复随机种子及可重现失败例。若暴力不能应对大输入，仅用于小规模对拍。
- **压力测试**：最大合法规模独立测，不强迫平方复杂度方法执行数十亿次；区分未运行与不通过。
- **溢出及特异性**：C/C++ 检查 `int` 或 `long long`；JS 检查安全整数；Python 大整数不易溢出但注意列表/递归栈；内存释放与栈边界需人工检查。

## 5. 交叉验证与结论写法

推荐记录：

```text
文章：真实题名（可附已核实的平台及题号）
静态检查：PASS / WARN / FAIL
C：gcc 编译通过；确定性输入 X 组；随机对拍 Y 组；异常 Z
C++：g++ 编译通过；……
Java：javac 编译通过；……
Python：python3 执行通过；……
JavaScript：node 执行通过；……
未验证项：……
发布 Markdown：<实际路径>
发布信息：<实际路径>
```

测试次数是**实际执行的检查数**；如果运行 X 条用例跨 5 种语言 3 解法，先区分“用例数 X”、“代码实现数 15”、“执行次数 15X”。不要把多重计数混为“测试覆盖率”。

## 6. 质量门禁

- P0 阻断发布：算法错误、示例预期错误、所选语言与中文步骤不符、代码组格式破坏、代码未闭合、输入输出接口明显错误、越界/未释放造成实际错误、数学证明伪命题。
- P1 必须改善：方法内部章节错序、没有中文执行步骤、核心行缺少解释、没有黑盒/白盒测试、复杂度没有推导、推荐失实。
- P2 可优化：格式词不统一、表格过长、文字啰嗦、重复说明、过密术语。

若时间有限，先确保 P0 正确，再完善可理解性，最后做可读性美化。
