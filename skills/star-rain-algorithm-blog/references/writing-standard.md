# 算法题解：写作与推理标准

## 目标读者与文字风格

读者拥有至少一门语言的基础语法知识，但不一定熟悉当前算法。读完某种解法后，应能解释原因、按步骤独立实现、处理边界、说明复杂度。术语首次出现用一句解释和一个小例子，不要长篇术语堆砌。所有内容必须像开发者写给读者的技术博客，而不是 AI 对工作过程的说明。

使用自然陈述，如“我们先固定左边界，再遍历右边界……”，避免“下面将为您生成”“不依赖语言”“人类可读步骤”“这是一种很神奇的方法”“极致性能、击败 100%”。适度使用二三级标题、Markdown 表格、行内代码与数学公式；不重复渲染题名 H1。

## 文章框架（来源无关，用户可指定结构）

```text
## 一、题目描述
  输入、输出、约束、样例、数学模型和易误解的细节
## 二、测试用例
  ### 2.1 黑盒测试：等价类与边界值
  ### 2.2 白盒测试：实际分支路径
  ### 2.3 扩展测试：大数据、随机对拍（按需）
## 三、解法一：……
  ### 3.1 核心思想
  ### 3.2 执行步骤
  ### 3.3 手工推演 / 正确性证明（必要时）
  ### 3.k 代码实现
  ### 3.k+1 复杂度分析
## 四、解法二：……
  同一套解法内次序
……
## N、总结：如何选择不同解法？
  完整横向比较表、推荐、依据、迁移边界
```

题目数量、解法数量决定编号，没有固定“必须五解”。文章不必另加“伪代码”“所有代码集中展示”等章节。若用户明确希望保留原题流程图，把它放在对应方法的“手工推演/图示”处，保持正确路径。

## 一、题目描述应达到的标准

1. 真实题名与来源；平台、题号、难度和链接仅在存在且可核实时写。自拟题标明设定，不伪装成官方题目。
2. 一段话还原任务；分点说明输入、返回、约束条件与关键规则。
3. 必要时用数学表达式 `$$…$$` 精确定义，如容器 `A(i,j)=min(h_i,h_j)(j-i)`；解释数学变量的含义。
4. 给至少一个完整样例（输入、输出、为什么）；指出为什么“看起来合理的错误理解”不成立。
5. 数据量如何约束候选算法（只作判断，不虚构 O(n²) 必然超时）。

## 二、测试用例怎么写

### 黑盒测试：在读代码前先明确对错

- 表列：`编号 | 输入 | 期望输出 | 测试目的/原因`。
- 合法输入优先，包括普通示例、最小合法长度、零/负/重复（前提是题目允许）、全相同、递增递减、嵌套或相交（若有）、最值与极限规模。
- 明确给出预期结果，复杂数据可描述生成规则和公式，不要写“待定”。
- 不要随意把 `null`、空字符串等题面排除的输入混入官方测试；工程扩展另标记。
- 若用户给旧测试用例，逐一手算/用可信 oracle 核对预期值。

### 白盒测试：对应后文真实控制分支

- 在第二节列出“计划覆盖”的重要控制分支/特殊状态以及选用的测试输入。
- 例如括号栈：左括号入栈、空栈遇到右括号、非空但类型不符、扫描结束非空；双指针：左短移动、右短移动、两侧相等、终止。
- 程序完成后复核表格：必须有真实代码路径触发；若仅列了用例但没收集覆盖率，不得声称“已达成 100% 分支覆盖”。
- 对递归/DP/搜索，覆盖基例、重叠子问题、剪枝、去重、状态越界等实际分支。

### 随机测试与对拍

使用可信的暴力解/小规模穷举作为对照；对随机短输入比较优化法输出，记录随机种子便于复现。多种未独立校核的算法相互一致，不能独自证明答案正确。性能压力测试与正确性测试分开。

## 三、按解法展开：读者的每一轮思考

### 核心思想

写出：

- 朴素可行性：怎样不漏地搜索/枚举答案。
- 当前瓶颈：哪些状态重复计算、哪些分支不可能更优。
- 优化观察：用数学关系或数据结构性质，解释哪些候选可以放心跳过。
- 本解法解决的问题：渐近提升、常数开销、代码可读性、扩展性分别表述。

进化可以是树状而非严格的一条性能链：比如“Map + Deque”可能比手写匹配更适合新增括号类型，但并非优于“数组模拟栈”的性能。给出新的方法时不要强行承诺全面优于前法。

### 执行步骤

推荐 5–10 条，但可根据复杂度增减：

1. 定义变量及初值，为什么选择这个初值。
2. 规定循环范围与继续条件。
3. 每轮首先读取或计算什么，为什么。
4. 依据当前状态分成哪些分支，各做什么。
5. 如何更新答案/辅助结构/指针。
6. 什么时候可以提前返回，为什么安全。
7. 为什么循环会终止、有无越界危险。
8. 返回什么，返回值为何正确。

以双指针为例，“移动较短的那块木板”不能只写这一句；还要写出当前面积怎么计算、为何要在移动前更新最大面积、较短端为何可以舍弃、等高时移动任一端为何安全、`left < right` 如何停止。用 1 个小型表格：`轮次 | left/right | 两端高度 | 面积 | 记录最大值 | 移动依据`。

### 正确性证明

- **枚举法**：展示覆盖所有合法候选与取最大值的逻辑。
- **双指针/贪心/剪枝**：证明被放弃的候选不可能让答案更好；不能只说“因为每次移动短板”。
- **二分**：证明单调性、区间缩减方式与边界更新。
- **DP**：定义状态、转移、基例及顺序，说明为何子问题完整。
- **栈**：明确维护的结构性不变量与什么时候出入栈。
- **回溯**：解释状态空间覆盖、恢复状态和剪枝安全性。

### 多语言代码与注释

重要语句注释“为什么”优先于“是什么”。每份至少包括初始化语义、核心循环/判断、关键状态变动和返回条件的必要注释；跨语言内容对应，避免出现 Java 特有流程与中文步骤不同。较长实现可以分段注释；避免逐行重复如 `i++ // i 增加一`。

代码接口匹配真实的运行契约：函数或类提交保留对应签名；ACM / 竞赛标准输入输出给出含入口、解析和输出的完整程序；自拟题先定义可调用接口或输入格式。默认一个解法一个五语言代码组，用户指定组合时按该组合输出。测试包装程序与正文实现分开，避免混淆提交格式。

### 复杂度

阐明用 `n` 表示输入大小，递归分析栈高、缓存个数等，注意：

- 双层枚举所有 `i < j`：候选为 `n(n-1)/2`，最坏 `O(n²)`。
- 双指针每次至少移动一端：至多 `n-1` 轮，所以 `O(n)`。
- `ArrayDeque` 和动态数组的摊还行为要准确区分。
- JavaScript `Number` 的整数精度限制、C/C++ 溢出、字符串不可变引起的复制等需与实际约束相匹配。
- 额外空间若引用的只是输入不计复制；构造 `toCharArray()` / `split('')` 可能确实额外分配，若分析为 `O(n)` 要讲清这部分。
- 描述最坏、最好、平均情形时必须标出所指，不用拍脑袋的“最优”“速度最快”。

## 总结与推荐

先给标准比较表：`解法 | 核心思想 | 时间 | 额外空间 | 优点 | 局限 / 适用场景`。再给实际选择建议，比如学习阶段从暴力入手、题目大规模应选 O(n) 解、规则高扩展性用配置/映射实现、有扎实基准证据才谈常数优化。最后用一句模式识别总结收束，例如：“可从两端候选中证明一端被淘汰 → 考虑对撞双指针。”

## 发布质量终审

文章能否只看步骤而不看代码重写？每张表的预期值是否正确？每个剪枝/指针决定有可解释的合法性？所选语言的接口和复杂度是否与实现一致？有无读者看了仍不知道哪个参数、哪个变量的含义？检查完再交付。
