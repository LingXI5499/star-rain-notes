# 异常、日志、测试与安全速查

分级与印刷页码来自《Java开发手册（嵩山版）》1.7.0。涉及安全机制时，应按现有框架及部署环境核对实现。

## 错误码和异常（第 29–32 页）

- **强制**：错误码应便于定位来源与团队沟通；不把版本号、错误等级编码进去。新增错误码先检查项目已有目录，避免语义重复。（第 29 页）
- **强制**：不要把可预检的 NPE、数组越界当作正常流程用 `catch` 处理，也不要用异常代替条件分支。按不稳定代码的异常类型分别处理；捕获后不能静默吞掉。对外层调用方给出可理解的错误。（第 30–31 页）
- **强制**：资源在退出路径中可靠关闭；支持的 JDK 上优先使用 try-with-resources。不要在 `finally` 返回。远程调用、自动拆箱与级联访问处检查可能的 null。（第 31–32 页）
- **推荐**：异常类型表达业务含义，保留根因；跨应用边界根据既有契约返回明确错误码或结果对象，不临时发明另一套错误格式。（第 31–32 页）

## 日志（第 32–34 页）

- **强制**：Java 应用优先使用统一的日志门面，如项目既有的 SLF4J；使用占位符而非字符串拼接输出参数。若参数求值本身代价较高，在构造日志参数前判断级别是否启用。异常日志保留有用上下文和堆栈，避免同一异常在多个层级重复记录；生产环境不以标准输出或 `printStackTrace()` 代替日志框架。（第 32–33 页）
- **强制**：不输出密码、令牌、身份证号等敏感信息；对涉及敏感操作的日志，确认项目与法规要求的留存和访问策略。2020 年手册给出六个月留存约定，实际执行以当前合规与运维要求为准。（第 33–34 页）
- **推荐**：区分系统异常与用户输入错误的日志级别，控制高频日志量；日志要能定位问题，也不能泄露隐私。不要为了记录日志而把完整对象盲目序列化为 JSON。（第 33–34 页）

## 单元测试（第 35–36 页）

- **强制**：单元测试遵循自动化、独立、可重复（AIR）；使用断言验证，不依赖人工查看输出、测试顺序或外部服务。核心业务增量代码应有相应测试，Java 测试放在项目约定的测试源集，常见为 `src/test/java`。（第 35 页）
- **推荐**：覆盖正常、边界、异常与回归路径。手册给出语句覆盖率 70%、核心模块语句与分支覆盖率 100% 的目标；实际门槛应结合风险、变更范围和项目约定，不为凑数字编写无意义测试。（第 35–36 页）

## 安全（第 37 页）

- **强制**：访问用户私有资源时做对象级权限检查；敏感信息展示时脱敏。对所有外部输入验证类型、范围、长度与业务约束，特别是分页、排序、批量和 URL 参数。
- **强制**：SQL 使用参数绑定，排序字段等无法绑定的标识符使用明确允许列表；输出到 HTML 的用户数据按上下文转义。状态变更请求按应用认证方式配置 CSRF 防护；外部重定向目标限制在允许范围。
- **强制**：短信、邮件、下单、支付等消耗资源或涉及资金的操作设置重放防护、频率或数量限制。采取何种机制取决于现有架构和威胁模型。
