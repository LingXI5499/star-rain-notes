**这轮测试又发现两个真实缺陷，都已修复并加了回归断言：**

1. **`AccountMapper.invitationColumns` 漏选 `accepted_by`**：`acceptInvitation` 会写这一列，但 5 条 invitation 查询共用的列清单里没有它，于是 `AdminInvitationEntity.acceptedBy` **恒为 null** —— 同一份 XML 自己写、自己读不出来。已补进列清单（全仓无人读该字段，所以不是线上 bug，但属于「写进去读不出来」的隐患）。
2. **`SeoNotificationMapper.enqueue` 没配 `useGeneratedKeys`**：全项目其它 insert 都配了，只有这条没有，入队后 id 恒为 null。当前调用方不读它，所以无线上影响；但「`enqueue` 后拿 `log.getId()` 去 `claim`」会静默失效（`WHERE id = null` → 0 行）。已补上。

**另有两个只记录、未改动的问题**（改动会触及业务语义，留给所有者决策）：
- **搜索相关性**：`sr_search_document` 的全文索引是 `WITH PARSER ngram`，查询走 `NATURAL LANGUAGE MODE`。ngram 把词切成 bigram，自然语言模式下命中任意一个 bigram 就得正分 —— 本机实测随机 15 字符词 `qzwxecrvbnm12345` 命中 **948 行**（最高 score 132），同一词的 `BOOLEAN MODE` 是 **0 行**。中文关键词正常，但较长的拉丁词/英文短语会带出大量无关结果。要改查询模式或 DDL 才能解决。
- **验证骨架与生产的时区口径不同**：生产 `application.yml` 有 `connection-init-sql: "SET time_zone = '+00:00'"`，而 `MapperXmlIntegrationSupport` 用裸 `UnpooledDataSource` 不执行它，本机 MySQL 会话时区是 UTC+8。凡把 Java 侧 `LocalDateTime` 与 SQL 的 `CURRENT_TIMESTAMP()` 相比的语句会差 8 小时。处理方式是在 `AccountMapperXmlTest` 里显式 `SET time_zone` 对齐生产（**没有改骨架**）。建议后续把这条 init SQL 也加进骨架，否则每个用到时间比较的新测试都会再踩一次。

### 1.3.2 测试发现的一个真实隐患（已修）

写 `AnalyticsMapperXmlTest` 时，第一条写入就撞上了非空约束：

```
Column 'referrer_category' cannot be null
```

`sr_analytics_event.referrer_category` 在库里是 `NOT NULL DEFAULT 'DIRECT'`，
而 XML 的 INSERT **显式写了这一列**——显式写入会**覆盖列默认值**，所以传 null 不是「回落到 DIRECT」
而是直接违反非空约束。而 `AnalyticsServiceImpl.safelyInsert` 会把这个异常**吞掉并只记一条 warn 日志**，
表现就是**页面浏览被静默丢掉**。

可达性：`ReferrerClassifier.classify()` 的五条分支都返回具体分类（DIRECT/INTERNAL/SEARCH/SOCIAL/OTHER），
所以当前生产路径**碰不到** null —— 这是隐患不是现网故障。
已把 XML 改成 `COALESCE(#{referrerCategory}, 'DIRECT')`，让语句尊重库声明的默认值，
并加了一条专门的回归用例。**这是本轮唯一一处刻意的行为改动**（只在原本就会失败且被静默吞掉的路径上生效）。

### 1.4 迁移顺带带来的三个实质改进

1. **分页从字符串拼接变成参数绑定**：原 `last("LIMIT " + pageSize + " OFFSET " + offset)` → `LIMIT #{limit} OFFSET #{offset}`。
2. **「部分列更新」变成显式列清单**：原 `updateById` 靠实体字段是否为 null 隐式决定更新哪几列，现在每条 UPDATE 写死了它更新哪几列。
3. **两处隐式的列更新语义被暴露并锁死**：`@TableField(updateStrategy = ALWAYS)` 的「null 也要写」与默认的「null 跳过」，在 XML 里分别变成「无条件 SET」和「`<if>` 包裹」，两种都有 DB 测试逐列断言。**这是最容易静默改业务行为的地方**（详见各验收文档第 3/4 节）。

### 1.5 P0 遗留（如实记录）

- `WorkMediaEntity.caption` 用 `<if test="caption != null">` 保留了「不传=保留旧值」的既有行为，
  代价是 **caption 无法被清空** —— 这是迁移前就有的缺陷，本轮只保行为不变，没有顺手改。
- 各模块 pom 仍保留 `mybatis-plus-spring-boot3-starter`：源码已零引用 `com.baomidou`，
  但 starter 仍提供 `SqlSessionFactory`/mybatis-spring 自动配置。**不要单模块摘除**，
  等确认没有模块再需要 MP 的其它能力后，统一换成 `mybatis-spring-boot-starter`。
- 全仓无 `PaginationInnerInterceptor`，所以分页不依赖 MP 插件，移除 `BaseMapper` 没有能力缺口；
  也没有模块使用逻辑删除 / 乐观锁 / 自动填充。

`star-rain-package-taxonomy` 目前只登记了 `api` = 「只有接口 + 契约 DTO」，
**建议所有者把 `api/vo` 补进那份规范**（按它自己的规矩「新增类别必须先写进规范，再建包」）。

**同名但不同形**（后者多 `id` / `createdAt` 且做了 Long→String 序列化，供后台「正在被谁引用」面板；
前者只暴露业务方需要的 5 个字段）。因此 `MediaReferenceApiAdapter` 里引用模块内那个必须写**全限定名**，
不能再加同名的 import —— 这一条已写进该类的类注释，避免下一个人「顺手」补 import 时踩坑。

### 3.3 已完成的「禁止 record」硬约定（全仓 record 清零）

项目规范明令禁止 Java record（理由：record 的访问器是 `id()` 而非 JavaBean 的 `getId()`，
与 `BeanUtils.copyProperties`、模板引擎等按 JavaBean 约定工作的库不兼容）。
本轮把**全仓最后 19 个 record 全部改成 Lombok POJO**：清单里的 16 个 + 额外发现的 3 个 `private record Window`
（analytics / media / search 三个限流器里的滑动窗口）。访问器改写 **175 处**，跨 21 个文件。

**完成判据**：全仓 `src/main/java` 与 `src/test/java` 里 **record 声明 = 0**（已用脚本复核两遍）。

**为什么这次迁移值得做、而且验证得比较重**：改 record 只动类型定义，**JSON 契约完全靠属性名**，
一旦某个属性名被顺手改掉，前端会静默失效。所以验证不是「测试通过」就算：
- 用**迁移前的 jar 与迁移后的 jar 各抓一次**同一组 14 个接口的「键路径 + 值类型」集合，逐项比对 → `ALL ENDPOINT KEY SETS IDENTICAL`；
- `javap` 反编译新 jar，确认 `GrammarDto$Curriculum` 上是 `getCourse()`/`builder()`/无参构造，`course()` 已消失；
- 离线 Jackson 探针 24 项断言（6 个 Request DTO 反序列化、逐字节 JSON 比对、`@AllArgsConstructor` 下旧的 `new Page(...)` 写法仍可用、`equals`/`hashCode` 仍为值语义）；
- `POST /api/admin/search/rebuild` → 200 且 `activeDocuments: 2234`，这条路径真实走到了 `getChapters()` / `getSearchableText()`。

**两个坑（值得记住）**：
1. 这 16 个 record **原本一个 Bean Validation 注解都没有**（英语接口的必填/长度校验是各 `*ServiceImpl` 里手写的），
   所以「把注解搬到字段上」这一步是 no-op —— 不要以为迁移顺带修好了校验。
2. `EnglishMapperXmlTest` 里的 `grammar.course()` / `grammar.sections()` **是 `GrammarMapper` 的接口方法，不是 record 访问器**；
   按属性名无脑替换会把它改坏。凡是「批量改访问器」的脚本都要先分清同名的 Mapper 方法。

`mvn -B -o -pl star-rain-site -am test` 全绿。

### 4.2 已修：邮件投递失败的审计搬回服务层（原先因为会丢日志而刻意留白）

`AccountController.sendEmailCode` 与 `AuthController.sendEmailVerificationCode` 原先各写了一段：

```java
try { ... } catch (ApiException exception) {
    if ("MAIL_DELIVERY_FAILED".equals(exception.getCode())) {
        audit.failed(actor, null, "EMAIL_CODE_DELIVERY_FAILED");
    }
    throw exception;
}
```

**不能 naive 搬**：`AccountAuditServiceImpl` 原先没有 `REQUIRES_NEW`，会加入调用方事务。
在 Controller 的 catch 里服务事务早已回滚，写审计落到自动提交上所以能活；
一旦搬进 `@Transactional` 的服务方法，这条审计会**跟着回滚一起消失**。

**做法**（不是靠 `TransactionSynchronization` 绕，而是把语义写进 API）：
1. `AccountAuditService` 新增 `failedIndependently(...)`，实现上标 `@Transactional(propagation = REQUIRES_NEW)`
   —— 挂起调用方事务、自己提交，专门用于「审计描述的是调用方这次失败」的场景。
   接口上写明了三个方法的区别：`success`/`failed` 加入调用方事务，`failedIndependently` 独立提交。
2. `EmailVerificationServiceImpl` 抽出 `deliver(email, code, actorId)`：发信失败时调 `failedIndependently` 再原样抛出；
   注册流程传 `actorId = null`，登录态流程传账号 id（与改动前两个 Controller 的 actor 取值一致）。
3. 两个 Controller 的 try/catch **整段删除**，并因此各少了一个 `AccountAuditService` 依赖与构造参数。

**回归测试** `EmailVerificationServiceMailFailureTest`（3 例，Mockito 注入邮件失败）钉住三件事：
发信失败确实调用的是独立事务版本（且**绝不**退化成会跟着回滚的 `failed`）、异常继续上抛、
验证码没有写库（发信失败就不该留下一个能用的验证码）。

### 4.3 顺带修掉一个「一点就炸」的 API

写上面那个测试时踩到：`AccountPrincipal` 挂着 `@Builder`，而它的全参构造器会执行 `Set.copyOf(roles)`
（这个规范化是有意的 —— 下游到处直接 `getRoles().contains(...)`，不能容忍 null）。
Lombok 的 builder 正是调用这个构造器，于是 `builder().accountId(x).build()` 这种「只设部分字段」的写法**直接 NPE**。
全仓检索确认**没有任何一处使用它**，所以直接删掉 `@Builder`，只保留构造器与 JavaBean 访问器。

`VocabularyPublicController` / `VocabularyStudyAccountController` 各一处，是发音代理对
「上游音频源不可用」的降级处理（返回 404 让前端回退到浏览器合成），属接入层的协议适配，可接受。

## 五、P2：事件、安全与特殊包 —— 已审查，无需改动

完整核对结果见 `docs/开发文档/后端架构收敛-P0进展与P1P2方案.md` 第五节，结论：

1. **事件**：7 个事件逐个核对了构造点与监听点（注意发布方用 builder，`new XxxEvent(` 搜不到，
   必须用 `XxxEvent.builder()` 找，否则会误判成「没有发布者」）。**全部既有发布者也有消费者，无死事件。**
   消费端失败是刻意吞异常并记日志（索引是派生状态，消费者失败不能把已提交的发布变成失败的 HTTP 响应），
   但没有补偿机制 —— 建议后续加失败计数/告警。
2. **安全**：第一轮已做（`SecurityRulePlan` + `SecurityPatternValidator` 拒绝 `denied × public`、
   `denied × authenticated` 的非挖空重叠，6 个回归用例钉住优先级）。
   **本轮补上了规则表的覆盖率测试** `SecurityRuleCoverageTest`（8 例，在 `star-rain-boot`）：
   它从源码树发现**全部 14 个真实贡献者**、反射实例化、走 `SecurityRulePlan.of()` 组装出真实规则序列，然后验证
   - 不变量：每条模式以 `/` 开头；没有模块声明了贡献者却一条规则都没有；**同一模式不会被两个模块声明成不同访问级别**（真正的安全缺陷）；
   - **关键路由的生效访问级别**（按顺序第一条命中的规则说了算，正是 Spring Security 的行为）：
     `/api/admin/accounts/1/roles` → DENIED、`/api/admin/accounts` → AUTHENTICATED、
     `/api/public/site/config` → PUBLIC、`/api/account/learning/plans` → AUTHENTICATED 等 11 条；
   - 未声明的路径 → 落到 `anyRequest().denyAll()`（**默认拒绝而不是默认放行**）；
   - `denied` 是「挖空」而非整段封死：`/api/admin/accounts/1/roles/extra` 仍落回 `AUTHENTICATED`，把实际行为钉住；
   - 顺序不变量用**真实模块规则**再验一次（`SecurityRulePlanTest` 用的是手写假贡献者）。
   贡献者数量与源码树扫描结果比对，新增模块忘了纳入验证会失败。
3. **特殊包**：`media/storage`、`english/vocabulary/storage` 的接口/`impl` 分层正确 ✅；
   `*/context`、`review/handler`、`tutorial/content/handler` 命名与职责一致 ✅；
   `site/provider` 里只有 `HomeSectionDisplayOptions` 不是 Provider（它是「按区块 config_json 解析展示参数」的组件），
   属唯一一处「一个包放了两类东西」，但它确实是 Provider 机制的合作者，留在原处可辩护。
   `common/dashboard` 承载 8 个模块实现的契约 —— 曾被称为「common 里装业务特性」，
   但它只是接口 + DTO，聚合逻辑在 `site`；要移走只能新建 API 模块（挪进 `site` 会因 site 依赖这 8 个模块而循环），
   收益不足，**建议保留并在规范里写明**。

   **本轮修掉的一处不一致**：两个「启动时补一次派生数据」的类原先分居不同深度 ——
   `search/service/SearchStartupRebuild` 在 `service`，而 `seo/event/SeoStartupRebuild` 在 `event`，
   这正好违反规范第一条铁律「同一种角色不允许分散在不同深度」（反例就是这个形状）。
   已把 `SeoStartupRebuild` 移到 `seo/service`：它监听的是 `ApplicationReadyEvent`（应用生命周期事件）
   而不是业务领域事件，本模块 `event` 包的语义是「领域事件消费者」（现在那里只剩 `SeoContentEventConsumer`）。
   类名保留 `Startup` 前缀，让「只在启动时跑一次」在名字上就看得出来。

   **审查后决定保留的**（非遗漏，逐条给理由）：
   - `analytics/service/AnalyticsDailyAggregationScheduler`：`@Component` + `@Scheduled`。
     全仓唯一的定时任务，所以不存在跨模块不一致；类名已经说清了它的角色；
     为它单独引入 `job` 包会触发规范「新增类别必须先写进规范，再建包」，收益不足。
   - `search/service/SearchStartupRebuild`：与 `SeoStartupRebuild` 同型（`ApplicationReadyEvent` + 调服务重建），
     名字与位置都自洽。
4. **领域事件的幂等性与失败处理（本轮逐个读完两个消费者后确认）**：
   `SearchEventConsumer` 与 `SeoContentEventConsumer` 的失败处理都是**刻意吞异常并记 error 日志**
   （索引/快照是派生状态，消费者失败不能把一次已提交的发布变成失败的 HTTP 响应），日志里都写了「run rebuild」。
   幂等性是**按构造保证**的：搜索侧按 contentId 重建/删除单条文档，SEO 侧按路由 `refreshRoute`/`removeRoute` 再入队
   UPSERT/DELETE；教程那条路径还显式算了 before/after 差集，把撤下的章节补发 DELETE。
   因此重复投递同一事件不会产生第二份数据。
   **唯一缺口是可观测性**：消费端持续失败时索引会静默变旧，无人知晓 —— 建议后续加失败计数/告警，
   或在启动时对索引做一次一致性抽查（这属于新增能力，不在本轮范围）。
