## 2. 本轮实际完成的工作

### 2.1 查询与评估

- 项目使用 **MyBatis-Plus 3.5.17（建立在 MyBatis 上）**，13 个 Maven 子模块依赖其 starter；不能称为“纯 MyBatis”。此前同时存在 XML、自定义 Mapper SQL 注解、`BaseMapper` 生成的 CRUD SQL。
- 检索未发现 Controller 直接注入 Mapper。不能据此推断所有 Controller 都没有业务逻辑；全项目逐方法审查仍未完成。
- `@Mapper` 是 Mapper 注册标记，`@Param` 是参数绑定标记，二者不是在 Java 中书写 SQL 的注解。

### 2.2 已落地的修改

1. 将原先 10 个 Mapper 接口中的 `@Select` / `@Insert` / `@Update` / `@Delete` 自定义 SQL 迁入 10 份 XML，涉及 analytics、message、portfolio、tutorial；共迁移约 39 个语句。全项目 Java 源文件中再检索不到这些 SQL 注解和 `JdbcTemplate`。XML 位于各模块 `src/main/resources/mapper/`。
2. Site 模块的 `HomeSectionMapper`、`SiteConfigMapper` 改成显式 Mapper 方法与 XML，去掉 `BaseMapper` 继承；Site 的两个实体去掉仅供 MyBatis-Plus 使用的表注解。
3. Site 的四个业务服务分为 `service` 接口和 `service/impl` 实现：`SiteConfigService`、`HomeSectionService`、`HomeAggregationService`、`DashboardAggregationService`。Controller 注入接口。
4. Site 的请求类型改用 `DTO` 后缀，响应类型移入 `vo`（跨模块公开契约在 `api/vo`）并改用 `VO` 后缀。包括 `SiteConfigPatchDTO`、`HomeSectionPatchDTO`、`SiteMediaRequestDTO`、`SitePublicConfigVO`、`SiteHomeVO`、`SiteDashboardVO` 等。对应调用与测试已同步。
5. 首页多来源区块的 Provider 策略从拥挤的 `site/service` 移到 `site/provider`；`HomeSectionLimit` 重命名为 `HomeSectionDisplayOptions` 以表明它只负责展示配置；删除未被实际调用的 `HeroSectionProvider`。
6. 博客“恢复文章”原先发布无人消费的 `BlogPostRestoredEvent`，搜索索引可能不更新。现在复用已有消费者处理的 `BlogPostPublishedEvent`，并调整测试。

### 2.3 为什么暂时保留 `event`、`security`、Provider

- `api/event` 中的事件承载跨模块状态变化，例如博客发布或撤回后更新搜索/SEO。跨模块事件有实际消费者，保留；只供内部使用、没有消费者的事件应删除，本轮删除了博客恢复事件。
- `ModuleSecurityContributor` 用于各业务模块提供 URL 权限规则，Account 模块集中构造唯一的 Spring Security 过滤器链。这个接口隔离模块与 Account 的直接依赖，暂时有必要。接手时应继续检查规则重叠、权限覆盖和接口命名，不应把安全规则随意挪回 Controller。
- 首页 Provider 解决教程、博客、作品等多来源区块的聚合，当前确有多个实现，保留一个 `provider` 包比把具体实现堆入 `service` 清楚。不要再为每个 Provider 建独立的 controller/service/mapper 子树。

## 4. 尚未完成：不要误认为已经达标

| 优先级 | 工作 | 现状与建议 |
| --- | --- | --- |
| P0 | 消除 `BaseMapper` 生成 SQL | 仍有 **28 个 Mapper** 继承 `BaseMapper`，集中在 tutorial、profile、portfolio、message、english。虽然自定义 SQL 注解已清零，但这些 Mapper 的 `selectById` / `insert` / `updateById` 等 CRUD 仍由 MyBatis-Plus 生成，**不符合“全部 SQL 在 XML”**。逐个定义显式方法、迁移调用和 XML，并做真实数据库验证。不要只删除继承导致运行时 `Invalid bound statement`。 |
| P0 | XML 运行时验证 | 对本轮迁入 XML 的 analytics、message、portfolio、tutorial Mapper 逐个执行代表性读写集成测试；现有 Maven 单元测试与三个公开 HTTP 冒烟不足以证明所有 XML 参数、结果映射都正确。测试写操作应使用事务回滚或隔离数据。 |
| P1 | 全项目 DTO/VO 命名与归类 | Site 已调整；其余 `dto` / `vo` 包下仍有约 **43 个生产类**不以 `DTO`/`VO` 结尾（另有 1 个测试类）。其中有 Command、Document、内部策略结果等，不能机械加后缀：先判定它究竟是传输对象、视图对象、领域模型还是基础设施对象，再重命名或移包。同步修改 JSON 契约和跨模块引用，保留前端字段兼容。 |
| P1 | Service 接口与实现 | Site 四个业务服务已分离；其他模块仍有不少具体 Service 直接放在 `service`。按职责评估，业务入口统一接口 + `Impl`；仅工具、策略、配置或生命周期类不必为了形式强建接口。避免“接口只有一个实现”但无稳定业务契约的过度设计。 |
| P1 | Controller 职责审查 | 目前只确认未发现 Controller 直接注入 Mapper。仍需逐方法审查输入校验、状态决策、事务、跨服务协调；把业务规则移到 Service，而路由、绑定、鉴权声明、响应转换留在 Controller。 |
| P2 | event/security 包审查 | 梳理事件发布者、消费者、幂等性与失败处理；没有消费者的事件删除。审查 `ModuleSecurityContributor` 规则表和统一链的顺序与覆盖测试。保留有价值的跨模块契约，删掉无效抽象。 |
| P2 | 其他特殊命名 | 按“文件名能说明职责”整理 `job`、`adapter`、`support`、`provider` 等包。启动时只执行一次的类可叫 `*Startup...` 并放 `config` / `lifecycle`；`adapter` 若实现跨模块接口，要明确它适配的边界；纯常量/工具不得混入 Service。先看引用关系，避免搬包造成循环依赖。 |
