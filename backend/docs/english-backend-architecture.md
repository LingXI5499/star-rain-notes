# 英语后端架构升级

## 当前判断

英语后端已经按听力、阅读、语法、写作、共享学习等业务域拆包，Controller、Service、Mapper、DTO 和 `@Valid` / `@Transactional` 也已在使用。因此问题不在“缺少注解”，而在部分 Service 同时承担多个资源的查询、命令、SQL 拼接和响应组装，职责边界不够清晰。

本次词汇改造以兼容现有 API、表和复习算法为前提，开始建立一致的纵向切片：

- Controller 只负责 HTTP 参数、校验和状态码。
- `VocabularyService` 负责公开词汇目录和词条读取。
- `VocabularyAdminService` 负责后台查询及分类、词条写入用例；写操作在服务边界开启事务，列表查询使用只读事务。
- `VocabularyLayer` 集中表达六个标准分类组，避免前后端继续自行解析 A/B/C 后缀。
- `VocabularyWordViewAssembler` 统一组合词条及音频、词族关联数据，不再把响应组装混在业务服务中。
- 词汇、听力、阅读、语法的内容查询统一使用只读事务；已有写入方法的 `@Transactional` 保持可写事务边界。

这一步保留了全部对外路由和现有表结构。词汇管理的一级分类筛选在服务层按 `layer_order` 过滤，避免页面选中分类后仍读取全库词条。

## 四级词库迁移约束

`V34` 补充主题用法字段；`V35` 从提供的分类文件生成 60 个主题和 7053 条分类归属（4190 个不同英文词）。同一英文词出现在多个主题时保留每一条归属。脚本先删除旧词条，再写入新词条，因此会触发数据库中依赖旧词条 ID 的级联清理；上线前应备份并确认旧词条学习记录的处理方式。

迁移由 Flyway 在应用启动时执行。不要用 MySQL 客户端单独运行版本脚本，否则业务数据已变化而 `flyway_schema_history` 未记录版本，下一次启动会校验失败。若恢复 V33 的数据库备份，让应用自动执行 V34 和 V35；若数据库已经手动执行过脚本，需要先核对结构、分类、词条数量和脚本校验和，再修正迁移历史。

## 后续重构顺序

后续按业务域小步拆分，不一次性改包名或重写所有 SQL；每步保持路由、响应字段和数据库行为兼容：

1. **听力**：将当前较大的 `ListeningItemService` 按听力内容、分段、发音规则和阅读配对拆成用例服务；避免一个服务同时编排多个资源。
2. **阅读**：区分文章目录查询、文章编辑命令和练习批改，集中管理阅读与语法/听力内容的关联查询。
3. **语法**：将课程配置与课程目录（章节、课时）拆开，发布状态校验继续放在课程用例边界。
4. **共享学习**：整理学习包编排、可发布性校验、推荐/分析读取之间的依赖，避免共享模块反向依赖具体 Controller。
5. **持久化边界**：优先把重复或复杂 SQL 收拢到 Mapper/Repository；简单单表 CRUD 保留现有 MyBatis-Plus。不要为了“统一”而机械地把所有 JDBC 改写成 XML。

## 兼容与安全约束

- 不改变词汇复习算法、复习间隔或账户学习接口。
- 新增或修改业务写入必须有明确事务边界；只读目录/统计查询使用只读事务。
- DTO 在 HTTP 边界用 Bean Validation；业务不变量仍由 Service 校验，不能只依赖前端。
- 删除内容前明确其外键级联影响；分类仅允许删除空分类，词条删除需在界面提示学习记录会级联清理。
- 每次只重构一个业务域，并以该域集成测试覆盖路由兼容、事务回滚、权限和关联数据；不以 Lombok 或更多注解替代清晰的职责拆分。
